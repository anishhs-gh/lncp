# Contributing to LNCP

LNCP is small and evolves deliberately. The frozen core stays stable; new
capability is added as **modules** and **minor versions**, never by changing
the meaning of existing packets.

## Proposing a change

Every change to the specification is a written proposal, opened as a GitHub
issue, that states:

1. **What** — the exact packets, fields, or registry entries added or changed.
2. **Why** — the real interoperability problem it solves.
3. **Class** — whether it is a *minor* or *major* change (see below).
4. **Compatibility** — how an older peer behaves when it encounters the new
   packets (the answer must follow the envelope tolerance rules in
   `spec/lncp-1/02-envelope.md §3`).

Once accepted, a proposal is not silently altered; it lands as a versioned
spec change with a changelog entry.

## Change classes

Per `spec/lncp-1/registry.md §6`:

- **Minor** (`1.0` → `1.1`): adds packet types, modules, capabilities, or error
  codes. Never alters the meaning of an existing value.
- **Major** (`LNCP/1` → `LNCP/2`): changes framing or envelope structure.
- A retired value is *reserved forever* and never reused.

## Ground rules for spec text

- Normative language uses **MUST / SHOULD / MAY** requirement levels.
- Every normative claim about bytes on the wire should be anchored to a test
  vector where practical.
- The spec stands on its own: it never defines itself by analogy to other
  protocols.

## Working on the reference library

```bash
cd reference
npm install
npm run typecheck   # strict, no emit
npm run build       # emits dist/ + .d.ts
npm test            # conformance + behavior tests
```

Requirements for a library change to merge:

- `npm run typecheck`, `npm run build`, and `npm test` all pass.
- New packet types come with builder functions, type guards, and tests.
- The library stays **pure**: it builds, parses, signs, and verifies packets,
  but never opens sockets. Transport wiring belongs to host programs.
- No new runtime dependencies without prior discussion.

## Conformance vectors

`vectors/vectors.json` is frozen output. If a change legitimately requires new
vectors:

1. Extend `vectors/generate.js` (deterministically — fixed seeds only).
2. Regenerate: `node generate.js > vectors.json`.
3. CI verifies the committed file reproduces exactly; a vector diff without a
   matching generator change will fail.

Existing vectors are never edited by hand.

## Release process

Releases are cut by the **Release** GitHub Actions workflow
(`.github/workflows/release.yml`), triggered manually from the master branch:

1. Land a release commit on master containing the `CHANGELOG.md` entry
   (`## [X.Y.Z]` — replace its `Unreleased` marker with the release date) and
   the matching `reference/package.json` version bump.
2. Run the **Release** workflow (Actions → Release → Run workflow) with the
   version number, whether to publish `@lncp/core` to npm (`publish-npm`),
   and the npm dist-tag (`latest` for stable, `beta`/`next` for prereleases —
   the workflow refuses to put a prerelease on `latest`).
3. The pipeline is: validate (master-only, version/changelog/tag consistency)
   → verify (typecheck, tests, build, vectors) → **npm dry-run** with strict
   auth → `npm publish --provenance` → `vX.Y.Z` tag + GitHub release.
4. Release notes are generated by
   [ledger](https://github.com/anishhs-gh/ledger) (`@anishhs/ledger`) from the
   commits and diffs since the previous tag, using Bedrock via the
   `BEDROCK_API_KEY` repo secret (optional repo variables: `LEDGER_MODEL`,
   `AWS_REGION`). If the secret is missing or generation fails, the release
   uses the curated `CHANGELOG.md` entry instead — notes never block a
   release.
5. Nothing is tagged or published locally by hand; the workflow is the single
   release path.
6. The spec version (`LNCP/MAJOR.MINOR`) only moves when normative text
   changes; a library-only fix is a patch release that does not touch the
   spec version.

### Publishability is checked continuously

CI runs the same **npm dry-run** workflow on every push and PR
(`.github/workflows/npm-dry-run.yml`): quality gates, build, a tarball
allowlist check (`reference/scripts/verify-pack.mjs` — the package ships
`dist/` + metadata only, enforced, not assumed), and `npm publish --dry-run`.
When the `NPM_TOKEN` secret is available it also verifies the token
authenticates and has publish permission, so an expired token surfaces on the
next push — not on release day. Fork PRs (which never receive secrets) skip
only the auth check. The workflow can also be dispatched manually from the
Actions tab to answer "would a publish succeed right now?".
