# LNCP/1 — File Transfer Module

The file transfer module provides **peer-to-peer file exchange** — the ability
for one peer to offer a file and another to accept, receive, and manage the
transfer. It is optional; a conformant implementation MAY implement it.

- **Module name (capability):** `file-transfer`
- **Packet types:** `FILE_OFFER`, `FILE_ACCEPT`, `FILE_REJECT`, `FILE_READY`,
  `FILE_CANCEL`, `FILE_PAUSE`, `FILE_RESUME`, `FILE_RESUME_REQUEST`
- **Reserved type-code range:** see `registry.md`

## 1. Purpose

File transfer enables peers to exchange arbitrary files without a central server.
The protocol supports:

- **Offer/accept/reject negotiation** — the receiver chooses whether to accept
- **Chunked transfer** — files are sent in manageable pieces over the existing
  TLS session
- **Pause/resume** — transfers can be paused and resumed, even after reconnect
- **Cancel** — either party can abort at any time

## 2. Transfer model

A file transfer follows this state machine:

```
                    ┌─────────────┐
                    │   IDLE      │
                    └──────┬──────┘
                           │ FILE_OFFER
                           ▼
                    ┌─────────────┐
           ┌────────│   OFFERED   │◄───────┐
           │        └──────┬──────┘        │
           │ FILE_REJECT   │ FILE_ACCEPT   │ FILE_CANCEL
           │               ▼               │
           │        ┌─────────────┐        │
           │        │  ACCEPTED   │────────┘
           │        └──────┬──────┘
           │               │ FILE_READY (sender ready)
           │               ▼
           │        ┌─────────────┐
           │        │ TRANSFERRING│◄────┐
           │        └──────┬──────┘     │
           │               │            │ FILE_RESUME
           │    FILE_PAUSE │            │
           │               ▼            │
           │        ┌─────────────┐─────┘
           │        │   PAUSED    │
           │        └──────┬──────┘
           │               │ FILE_CANCEL / FILE_RESUME
           │               ▼
           └───────►┌─────────────┐
                    │  COMPLETED  │
                    └─────────────┘
```

## 3. FILE_OFFER

The sender offers a file to the receiver. The receiver may accept or reject.

```json
{
  "v": "1.0",
  "type": "FILE_OFFER",
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "filename": "document.pdf",
  "size": 1048576,
  "hash": "sha256:abc123...",
  "chunkSize": 65536
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `id` | string | REQUIRED | Unique transfer ID for this file. Generated by the sender; used to correlate all subsequent packets. |
| `filename` | string | REQUIRED | The file's name, UTF-8. The receiver **SHOULD** sanitize before saving (remove path separators, limit length). |
| `size` | integer | REQUIRED | Total file size in bytes. |
| `hash` | string | OPTIONAL | Content hash for integrity verification. Format: `algorithm:hex` (e.g., `sha256:abc123...`). |
| `chunkSize` | integer | OPTIONAL | Proposed chunk size for transfer. Defaults to 64KB if omitted. |

Rules:

- The sender **MUST NOT** begin transferring file data until the receiver sends
  `FILE_ACCEPT` and the sender responds with `FILE_READY`.
- The `id` **MUST** be unique across all active transfers between the two peers.
- The receiver **SHOULD** display the offer to the user and await acceptance
  or rejection.

## 4. FILE_ACCEPT

The receiver accepts the file offer.

```json
{
  "v": "1.0",
  "type": "FILE_ACCEPT",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "chunkSize": 32768
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID from `FILE_OFFER.id`. |
| `chunkSize` | integer | OPTIONAL | Negotiated chunk size. The sender **SHOULD** use the minimum of its offered size and the receiver's requested size. |

Rules:

- After receiving `FILE_ACCEPT`, the sender **SHOULD** respond with `FILE_READY`
  before beginning the transfer.
- The receiver **MAY** request a smaller `chunkSize` to accommodate memory
  constraints.

## 5. FILE_REJECT

The receiver rejects the file offer.

```json
{
  "v": "1.0",
  "type": "FILE_REJECT",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "reason": "declined"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID from `FILE_OFFER.id`. |
| `reason` | string | OPTIONAL | Reason for rejection. See §5.1. |

### 5.1 Rejection reasons

| Reason | Meaning |
|--------|---------|
| `declined` | User declined the offer. |
| `busy` | Receiver is busy with another transfer; try again later. |
| `insufficient_space` | Not enough storage space. |
| `unsupported_type` | File type not supported. |
| `too_large` | File exceeds receiver's size limit. |

The sender **MUST NOT** retry immediately after `FILE_REJECT`. The receiver
may accept a later offer for the same file.

## 6. FILE_READY

The sender confirms it is ready to begin the transfer.

```json
{
  "v": "1.0",
  "type": "FILE_READY",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID. |

Rules:

- The sender **MUST** send `FILE_READY` after receiving `FILE_ACCEPT`.
- Upon receiving `FILE_READY`, the receiver **SHOULD** prepare to receive chunks.
- After sending `FILE_READY`, the sender **MAY** begin sending file chunks over
  the established TLS session. Chunk encoding is implementation-defined but
  **SHOULD** use binary framing within the session.

## 7. FILE_CANCEL

Either party cancels the transfer.

```json
{
  "v": "1.0",
  "type": "FILE_CANCEL",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "reason": "user_cancelled"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID. |
| `reason` | string | OPTIONAL | Reason for cancellation. |

Rules:

- Either the sender or receiver **MAY** send `FILE_CANCEL` at any point after
  `FILE_OFFER`.
- Upon receiving `FILE_CANCEL`, the other party **MUST** stop the transfer and
  discard any partial data (receiver) or cleanup resources (sender).
- The receiver **SHOULD** delete any partially downloaded file.

## 8. FILE_PAUSE

The receiver pauses the transfer.

```json
{
  "v": "1.0",
  "type": "FILE_PAUSE",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID. |

Rules:

- Only the receiver **MAY** send `FILE_PAUSE`.
- Upon receiving `FILE_PAUSE`, the sender **MUST** stop sending chunks.
- The sender **SHOULD** retain the transfer state to allow resumption.
- The receiver **MAY** send `FILE_RESUME_REQUEST` to restart the transfer.

## 9. FILE_RESUME_REQUEST

The receiver requests resumption of a paused transfer.

```json
{
  "v": "1.0",
  "type": "FILE_RESUME_REQUEST",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "offset": 327680
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID. |
| `offset` | integer | OPTIONAL | Byte offset to resume from. Defaults to 0 (restart from beginning). |

Rules:

- The receiver **MAY** specify an `offset` to resume from a specific point
  (e.g., if partial data was saved).
- The sender **MUST** respond with `FILE_RESUME` confirming the offset, or
  `FILE_CANCEL` if it cannot resume.

## 10. FILE_RESUME

The sender confirms resumption from a specific offset.

```json
{
  "v": "1.0",
  "type": "FILE_RESUME",
  "re": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "offset": 327680
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `re` | string | REQUIRED | The transfer ID. |
| `offset` | integer | REQUIRED | The byte offset the sender will resume from. |

Rules:

- The sender **MUST** send this after receiving `FILE_RESUME_REQUEST`.
- The `offset` **SHOULD** match the receiver's requested offset; if it cannot,
  the sender **MAY** send a different offset (e.g., chunk-aligned).
- After sending `FILE_RESUME`, the sender **MAY** resume sending chunks from
  the specified offset.

## 11. Transfer completion

A transfer is complete when the receiver has received all `size` bytes. The
receiver **SHOULD** verify the `hash` if one was provided in `FILE_OFFER`.

Upon successful completion:

- The receiver **MAY** send an implicit acknowledgement by closing the transfer
  context. No explicit "complete" packet is required.
- The receiver **SHOULD** persist the file to its final destination.
- Both parties **SHOULD** discard the transfer state.

## 12. Capability advertisement

A peer that implements this module **SHOULD** advertise the `file-transfer`
capability during capability negotiation (`registry.md → Capabilities`).

## 13. Acknowledgement classification

Per `02-envelope.md §4`, this module classifies its packets:

| Packet | Class |
|--------|-------|
| `FILE_OFFER` | acknowledged (expects `FILE_ACCEPT` or `FILE_REJECT`) |
| `FILE_ACCEPT` | acknowledged (expects `FILE_READY`) |
| `FILE_REJECT` | fire-and-forget |
| `FILE_READY` | fire-and-forget |
| `FILE_CANCEL` | fire-and-forget |
| `FILE_PAUSE` | fire-and-forget |
| `FILE_RESUME_REQUEST` | acknowledged (expects `FILE_RESUME` or `FILE_CANCEL`) |
| `FILE_RESUME` | fire-and-forget |

## 14. Security considerations

- The receiver **MUST** sanitize `filename` to prevent path traversal attacks.
  Remove or escape path separators (`/`, `\`), limit length, and avoid
  overwriting existing files without user consent.
- The receiver **SHOULD** verify `hash` after transfer to detect corruption or
  tampering.
- The sender **SHOULD** respect `size` limits and not send more data than
  advertised.
- Transfers occur over the existing TLS session; no additional encryption is
  required.
