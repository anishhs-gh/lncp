# LNCP/1 — Voice Module

The voice module provides **real-time audio calls** between peers over the local
network. It is optional; a conformant implementation MAY implement it.

- **Module name (capability):** `voice`
- **Packet types:** `CALL_OFFER`, `CALL_ACCEPT`, `CALL_REJECT`, `CALL_BUSY`,
  `CALL_END`
- **Reserved type-code range:** see `registry.md`

## 1. Purpose

Voice calling enables peers to have real-time audio conversations without a
central server or external service. The module defines:

- **Signaling** — call offer, acceptance, rejection, and termination over the
  existing TLS control channel
- **Media transport** — encrypted audio frames over UDP, separate from the
  control channel
- **Session management** — only one active call per peer pair; busy signal for
  additional incoming offers

## 2. Call model

A voice call follows this state machine:

```
                    ┌─────────────┐
                    │   IDLE      │
                    └──────┬──────┘
                           │ CALL_OFFER (caller sends)
                           ▼
         ┌─────────────────┴─────────────────┐
         │                                   │
    CALL_REJECT                        CALL_ACCEPT
    CALL_BUSY                               │
         │                                   ▼
         │                           ┌─────────────┐
         │                           │  IN_CALL    │
         │                           └──────┬──────┘
         │                                  │ CALL_END (either side)
         │                                  │ or session close
         └─────────────────────────────────►▼
                    ┌─────────────┐
                    │   ENDED     │
                    └─────────────┘
```

## 3. CALL_OFFER

The caller initiates a voice call by sending an offer.

```json
{
  "v": "1.0",
  "type": "CALL_OFFER",
  "callId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "from": {
    "id": "9f8b7c6d-1e2f-4a3b-8c9d-0e1f2a3b4c5d",
    "nickname": "alice",
    "discriminator": "a1b2"
  },
  "mediaPort": 49152,
  "key": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `callId` | string | REQUIRED | Unique identifier for this call session. Generated by the caller. |
| `from` | object | REQUIRED | Caller identity summary: `{ id, nickname, discriminator }`. |
| `mediaPort` | integer | REQUIRED | UDP port the caller is listening on for audio frames. |
| `key` | string | REQUIRED | Shared AES-256 key for encrypting audio, hex-encoded (64 characters). Sent over the TLS-encrypted control channel. |

Rules:

- The caller **MUST** generate a unique `callId` for each call attempt.
- The caller **MUST** generate a fresh random `key` for each call (not reused
  across calls).
- The caller **MUST** bind to `mediaPort` before sending `CALL_OFFER`.
- The `key` is transmitted over the existing TLS session; the UDP media path
  uses this key directly for encryption.

### 3.1 Ringing timeout

The caller **SHOULD** implement a ringing timeout (recommended: 30 seconds). If
no `CALL_ACCEPT`, `CALL_REJECT`, or `CALL_BUSY` is received within this window,
the caller **SHOULD** send `CALL_END` to the callee and clean up the call state.

## 4. CALL_ACCEPT

The callee accepts the incoming call.

```json
{
  "v": "1.0",
  "type": "CALL_ACCEPT",
  "callId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "from": {
    "id": "8e7d6c5b-4a3f-2e1d-0c9b-8a7b6c5d4e3f",
    "nickname": "bob",
    "discriminator": "c3d4"
  },
  "mediaPort": 49153
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `callId` | string | REQUIRED | The call ID from `CALL_OFFER`. |
| `from` | object | REQUIRED | Callee identity summary. |
| `mediaPort` | integer | REQUIRED | UDP port the callee is listening on for audio frames. |

Rules:

- The callee **MUST** use the same `key` from `CALL_OFFER` for media encryption.
- The callee **MUST** bind to `mediaPort` before sending `CALL_ACCEPT`.
- Upon receiving `CALL_ACCEPT`, both parties **MAY** begin sending audio frames
  to each other's `mediaPort`.

## 5. CALL_REJECT

The callee declines the incoming call.

```json
{
  "v": "1.0",
  "type": "CALL_REJECT",
  "callId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `callId` | string | REQUIRED | The call ID from `CALL_OFFER`. |

Rules:

- The caller **MUST** treat `CALL_REJECT` as a declined call and clean up state.
- The caller **MUST NOT** immediately retry the call; wait for user action.

## 6. CALL_BUSY

The callee is already in another call and cannot accept.

```json
{
  "v": "1.0",
  "type": "CALL_BUSY",
  "callId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `callId` | string | REQUIRED | The call ID from `CALL_OFFER`. |

Rules:

- A peer that is already in a call **MUST** respond to additional `CALL_OFFER`
  packets with `CALL_BUSY` rather than `CALL_REJECT`.
- The caller **MAY** interpret `CALL_BUSY` differently from `CALL_REJECT` in the
  UI (e.g., "user is on another call" vs. "user declined").

## 7. CALL_END

Either party terminates an active (or ringing) call.

```json
{
  "v": "1.0",
  "type": "CALL_END",
  "callId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| Field | Type | Presence | Meaning |
|-------|------|----------|---------|
| `callId` | string | REQUIRED | The call ID being terminated. |

Rules:

- Either the caller or callee **MAY** send `CALL_END` at any time after the call
  was initiated.
- The caller **SHOULD** send `CALL_END` if the ringing timeout expires without
  an answer.
- Upon receiving `CALL_END`, the other party **MUST** stop sending audio frames,
  close the media socket, and clean up call state.
- `CALL_END` is idempotent; receiving multiple `CALL_END` packets for the same
  `callId` is not an error.

## 8. Media transport

Audio is transmitted over UDP, separate from the TLS control channel.

### 8.1 Encryption

Each audio frame is encrypted with AES-256 using the shared `key` from
`CALL_OFFER`. The specific mode (e.g., AES-GCM, AES-CTR with sequence number)
is implementation-defined. The encryption ensures confidentiality of the audio
stream; the key was exchanged over the authenticated TLS channel.

### 8.2 Audio format

The audio format is implementation-defined. Implementations **SHOULD** use a
standard format such as:

- **Opus** — efficient, low-latency codec ideal for real-time voice
- **PCM (16-bit, 48kHz mono)** — uncompressed, simple, low CPU

Implementations **SHOULD** negotiate the format out-of-band (e.g., in `CALL_OFFER`
and `CALL_ACCEPT` via extension fields) or agree on a default.

### 8.3 Jitter and packet loss

Implementations **SHOULD** include:

- **Jitter buffer** — smooth playback despite variable network latency
- **Sequence numbers** — detect and handle out-of-order or lost frames
- **Comfort noise** — fill gaps during packet loss rather than silence

These are implementation details; the protocol does not mandate specific
algorithms.

### 8.4 Port selection

The `mediaPort` **SHOULD** be chosen from the ephemeral port range (49152–65535)
or a dedicated range configured by the implementation. The port **MUST** be
reachable by the peer on the local network.

## 9. Session constraints

### 9.1 One call at a time

A peer **MUST NOT** have more than one active call. If a peer receives a
`CALL_OFFER` while already in a call, it **MUST** respond with `CALL_BUSY`.

### 9.2 Peer left handling

If a peer disconnects (session closes, discovery timeout) during an active
call, the remaining peer **MUST** treat this as an implicit `CALL_END` and
clean up call state.

## 10. Capability advertisement

A peer that implements this module **SHOULD** advertise the `voice` capability
during capability negotiation (`registry.md → Capabilities`). Peers that do not
advertise `voice` will not be able to initiate or receive calls.

## 11. Acknowledgement classification

Per `02-envelope.md §4`, this module classifies its packets:

| Packet | Class |
|--------|-------|
| `CALL_OFFER` | acknowledged (expects `CALL_ACCEPT`, `CALL_REJECT`, or `CALL_BUSY`) |
| `CALL_ACCEPT` | fire-and-forget (the media session begins) |
| `CALL_REJECT` | fire-and-forget |
| `CALL_BUSY` | fire-and-forget |
| `CALL_END` | fire-and-forget |

## 12. Future extensions (reserved)

The voice module may be extended in future minor versions to include:

- Video support (`video` capability, `VIDEO_OFFER`, `VIDEO_ACCEPT`, etc.)
- Call hold/resume
- Multi-party calls (conferencing)
- DTMF signaling

These are not defined in LNCP/1; the packet type range `0x0300–0x03FF` is
reserved for voice/media extensions.
